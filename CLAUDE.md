# Project context: SQL for Product Analytics (weekly LinkedIn series)

Eduardo publishes one LinkedIn post per week. Each post presents a product-analytics case with 8 questions of increasing difficulty (aggregations → JOINs → subqueries → window functions), mixing SQL and business analysis. Readers solve it in a free, browser-based SQL playground hosted on GitHub Pages from `docs/`.

## Decisions already made
- **Bilingual PT/EN.** Every page has a PT/EN toggle (`#pt` / `#en` in the URL). Post copy is written in both languages.
- **Engine: SQLite via sql.js (WebAssembly), static site, no server.** Chosen over DuckDB-WASM (too heavy to self-host), Streamlit (sleeps when idle, server-bound, URL not ours) and Abacus.AI (credit costs scale with traffic, lock-in).
- **Data:** synthetic CSVs generated by Python scripts in `generators/` (fixed seed). The page loads the CSVs into an in-memory SQLite DB at startup (`CREATE TABLE` + batched inserts in `index.html`).
- **Each question gets** a business framing, a hint, and a hidden solution with takeaways. Realistic traps (duplicates, immature cohorts, hypotheses the data rejects) are part of the format.
- **LinkedIn format:** case + questions in the post (ideally a PDF carousel), playground link in the first comment, solution walkthrough the following week.
- **Hosting:** GitHub Pages, branch `main`, folder `/docs`. URL: `https://<user>.github.io/sql-product-analytics/`.

## Target audience
People who work on product but aren't the most technical in the squad: PMs, POs, junior Data/BI analysts. Keep language plain, business framing concrete (a stakeholder asking for something), hints that nearly give the syntax.

## Question structure (8 per week)
- Q1–Q2: aggregations (COUNT, COUNT DISTINCT, GROUP BY)
- Q3–Q4: JOINs with aggregation
- Q5–Q6: subqueries (WHERE … IN / NOT IN, subquery in FROM)
- Q7–Q8: window functions (running totals, LAG, FIRST_VALUE)
Each question: context (who asks and why), the ask, concept chips, hint, solution + takeaways.

## Week 01: The Signup Funnel (done)
Fictional app "Trilha" (language learning). Tables `users` (9,000 rows) and `events` (~18k rows: landing_view → signup → onboarding_complete → first_purchase). Period 2026-09-01 → 2026-11-15. Onboarding v2 shipped 2026-10-15.
- Q1 visitors by channel · Q2 COUNT(*) vs COUNT DISTINCT (2,402 signup events vs 2,334 users)
- Q3 signup rate by device (desktop 26.7% vs mobile 25.5%: hypothesis rejected) · Q4 signup→paying by channel (paid_social 3.4% vs referral 23.4%)
- Q5 November signups without onboarding (222 users, CRM list) · Q6 onboarding rate before/after v2 (46.2% → 58.7%, signups before Nov 9)
- Q7 running total of paying customers (crossed 200 on Oct 28) · Q8 funnel with % of top and % of previous step
Generator: `generators/week01_signup_funnel.py 5` (seed 5).

## How pages are built
`templates/week-NN.html` holds the page (questions/text in the `Q` array, PT+EN; no answers). Answers live in `solutions/`, which is **gitignored** (local only, never pushed): `week-NN-<theme>.sql` (split by `-- QN ---` markers) and `week-NN-takeaways.json` (`[{"en":[...],"pt":[...]}, …]`, one per question). `python build.py NN` writes `docs/week-NN/index.html` with solutions **locked** (hints only, no answers in the HTML). The following week, `python build.py NN --solutions` releases them. Never edit the docs HTML directly.

## Adding a week
1. New generator in `generators/`, verify the planted signals by running the solutions against the data (python `sqlite3`).
2. Copy `templates/week-01.html` → `templates/week-NN.html` and edit the case text, the `Q` array and the `CREATE TABLE`/load block. Write `solutions/week-NN-<theme>.sql` and `solutions/week-NN-takeaways.json`. Create `docs/week-NN/` with the CSVs, `sql-wasm.js` and `sql-wasm.wasm`, then run `python build.py NN`.
3. Add the week card to `docs/index.html` and to the README table.
4. Test locally: `cd docs && python -m http.server 8000`.
